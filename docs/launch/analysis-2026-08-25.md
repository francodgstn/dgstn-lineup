## A. BLOCKS A CUSTOMER

### A1. Any authenticated principal can make themselves OWNER of any team `[V — rule text, not executed]`
**What:** `firestore.rules:457-462` — the self-provision disjunct `isAuthed() && memberId == request.auth.uid && request.resource.data.role == 'owner'` references **nothing about `teamId`**. `isTeamMember()` is existence-only (`:63-65`); `hasTeamRole()` reads the role off that same doc (`:75-83`); team `delete` is owner-gated (`:425-426`). Team ids are anonymously enumerable via the unconditional `match /{path=**}/public_profile/{id} { allow read }` (`:1412-1414`). A passwordless contact session (`contact:{id}`) and a kiosk token (`kiosk:{teamId}`) both satisfy `isAuthed()`.
**Breaks:** Entry price is "book one public class at any Linyup studio". Attacker becomes full owner of any tenant: all contact PII, `finance_transactions`, waiver ledgers, Stripe Connect config, plus `allow delete` on the team doc. GDPR-reportable breach class. Present since c1297577; no rules test covers it.
**Do:** Narrow to a create on the caller's own team — `resource == null && get(/databases/$(database)/documents/teams/$(teamId)).data.createdBy == request.auth.uid` (signup already writes `createdBy` first, `apps/web/src/lib/provisioning.ts` ~:120 before :158). Reject `contact:`/`kiosk:`-prefixed uids on that branch. Add the case to `tenantGovernance.rules-test.ts`. **Run it against an emulator before and after** — no lane executed it. Deploy rules to all three envs.
**Effort:** small. **Do this first, today.**

### A2. Prod web app and operator console run in `us-central1` while the DPA says Switzerland `[V]`
**What:** All five App Hosting backends (prod `linyup-web` + `linyup-admin`, staging ×2, sandbox) are `us-central1`; confirmed twice (App Hosting API + `gcloud run services list`). Firestore and all 228 functions are correctly `europe-west6`. Against that: `apps/landing/src/pages/dpa.md:89` puts **Hosting** in the "Switzerland (europe-west6, Zurich)" row and `:109` states "Application data is processed in Switzerland"; `privacy.md:80,85` repeat it. `infra/README.md:248` already records the gap.
**Breaks:** The SSR tier that terminates every request, holds payloads and Firestore results in memory, and writes logs is in Iowa. The DPA is a contract a studio signs, and it is false on a point counsel will check — discoverable with `dig`. Data *at rest* genuinely is in Zurich.
**Do:** Pick a side before the DPA goes to any founder. Either stand up `linyup-web-eu`/`linyup-admin-eu` in europe-west4 and cut domains over per `infra/README.md:248-268` (region is immutable → new backend + DNS cutover), or amend `dpa.md`/`privacy.md` to say compute is in the US under SCCs with storage in europe-west6.
**Effort:** medium (doc amendment: trivial).

### A3. No off-project backup, no restore runbook, no rehearsal `[V]`
**What:** Merged from two lanes, which **disagreed on severity** (ops-deploy: high; ops-data-safety: low, on the strength of project soft-delete + `DELETE_PROTECTION_ENABLED`). Facts both agree on: prod has PITR (7d window), delete protection, and a daily managed schedule at the 14-week max with 7 READY backups — **all inside `linyup-prod`**. `gcloud storage buckets list` shows no export bucket in any project. `infra/modules/firestore/main.tf:46-51` says the off-project copy "is tracked separately" — it is tracked nowhere. `docs/launch/restore-runbook.md` **does not exist**, and `.claude/agents/ops-agent/AGENT.md:170-172` instructs the operator to refuse to improvise without it (and at `:167` misnames managed backups as "scheduled exports").
**Breaks:** "We have backups" is verified; "we can restore" is untested. Recovery is contingent on `linyup-prod` continuing to exist (billing lapse, compromised owner, Google-side action). In an incident the one doc an operator opens disclaims itself.
**Do:** (a) Write `docs/launch/restore-runbook.md` covering PITR read-at-timestamp, managed-backup restore into a scratch DB (**answer: how do you get it back into `(default)` behind delete protection, and what do Functions/App Hosting point at meanwhile**), and Storage object restore. (b) Rehearse one restore, record elapsed time. (c) Add a scheduled `gcloud firestore export` to a bucket in a **different** project, or delete the comment claiming coverage and record the accepted risk. (d) Fix `AGENT.md:167`.
**Effort:** medium.

### A4. Studio self-deletion silently destroys every waiver signature ever collected `[V]`
**What:** `scripts/lib/exportConsentLedger.ts:1-28` frames itself as the gate on "the teardown path". `requireConsentExport` has exactly two call sites: `reset-sandbox-db.ts:227` and `seed-lead.ts:560` — **the two paths that never needed it**. `scripts/purge-team.ts` (its own header: "the one tool here that legitimately runs against production") does not import it, and `purgeScheduledTeams.ts:63` calls `purgeTeam(teamId, false)` with no export. Waiver acceptances/signers/versions live under `documents/*`, which is in `TENANT_DATA_COLLECTIONS` and recursively deleted (`purgeTeam.ts:57`).
**Breaks:** A studio using the DPA §4.8 30-day self-service deletion loses every liability release, permanently, with no artefact and no warning — and so does Linyup, in any dispute that follows. The file's own argument ("the ONE artefact a studio needs AFTER the relationship ends") applies exactly where the gate is missing.
**Do:** Mount `requireConsentExport` on `purge-team.ts` and on `purgeScheduledTeams` before `purgeTeam`. The scheduled path runs in Cloud Functions with no local disk → must write to **GCS**, not a runner filesystem. State the `purgeUnverifiedSignups` exemption in the header rather than leaving it inferred.
**Effort:** small.

**Effort:** small.

**Effort:** small.

### A7. Deploy precondition #3 is wrong in two directions — and one of them publishes studios' partner deals `[V, with a lane disagreement]`
**What:** `docs/launch/staging-review-2026-08-24.md:92-96` says `scripts/backfill-public-subscription-types.ts` "already touches every subscription type of every team", so running it materialises `partner_apps`. Three lanes independently disproved it at `:52-62`: the only write is `update({public:true})`, guarded by `if (!isActiveAggregator || alreadyPublic) continue`. So:
- **It writes nothing** for teams with no aggregator types, or whose aggregator types are already `public: true`. Live check: **every** subscription type in `linyup-sandbox` is already `public: true` → the sweep is a total no-op there, prints "0 candidates", and gets ticked off. `partner_apps` stays absent → `BookingForm.tsx:455` hides the fitness-app question → a studio selling via ClassPass/FitPass silently never captures `acquisition_partner_app`.
- **Where it *does* write**, it applies pre-2026-06-11 semantics the code has since reversed. `syncTeamPublicProfile.ts:437-441`: public==true "a partner type usually is not — a studio does not sell FitPass in its own shop." `--apply` puts every legacy partner type + its `payoutPerVisit` commercial terms into the studio's world-readable shop and pricing table as a (usually price-less) offer card.
**Lanes disagreed on how loud to be:** seed-emulator called it a **blocker**; ops-data-safety noted prod's DB was created 2026-06-05 (six days before the filter shipped) and the HMD migration writes `public: true` explicitly, so real prod exposure is "plausibly zero". Treat as: *do not run blind; the dry-run is cheap and settles it.*
**Do:** (1) Dry-run against each env and **read the per-document list**; do not `--apply` unless every named type is one the studio actually sells. (2) Replace the precondition with a script that materialises `partner_apps` unconditionally per team — a no-op merge on every `subscription_types` doc, or a direct `resolveTeamPartnerApps` → `public_profile` write. (3) Correct `staging-review-2026-08-24.md:92-96`; it is the sentence someone will act on. (4) Mitigating fact: `syncTeamPublicProfile.ts:391` writes `partner_apps` on **any** team-doc write, so a studio that edits its name self-heals — urgency is lower than the ranking suggests, correctness of the doc is not.
**Effort:** small.

### A9. `hasTeamCapability` fails **open** for any member doc lacking a `capabilities` field `[V]`
